## 1. Scope and what "product board" means

In this page a **product board** is a board with an NXP i.MX RT1062 (RT1060 family) that is not the RT1060-EVK Rev B (EVKB). Two variants are covered:

- **NOR variant:** the boot image and the application slots are in a serial NOR on FlexSPI, as on the EVKB.
- **eMMC variant:** the boot image is in an eMMC boot partition or user area, and the slots are in the eMMC user area.

The merged composition is for one board (**Verified in repository**): the four files in `zephyr/boot/boards/mimxrt1060_evk_mimxrt1062_qspi_B/`, the check script [`scripts/test-boot-composition.sh`](../scripts/test-boot-composition.sh) and the test `tests/build/test_boot_composition.py`. The composition page says: "Another board needs its own four files, and a build for it is a separate result." It describes the EVKB only. The RT1170 is out of scope here. The records of its desk investigation are separate and do not apply to an RT1062.

Not every statement about the EVKB is a statement about the RT1062. The boot header layout, the SoC memory map and the MCUboot logic belong to the SoC and the software. The flash part, the SDRAM, the pins, the switches and the bench values belong to one board. Section 3 separates them row by row.

**Where a product's files live.** A product's four composition files and its board devicetree belong in the product's own repository. Product board support stays out of this public repository (plan, section 10), and the [product composition guide](product-composition.md) puts board choices with the product. The folder `zephyr/boot/boards/<board>/` is where Crux keeps the EVKB files. Where the boot hooks of a product go is not decided (plan, section 8).

### Which files a product board adds or edits

A summary of the table above, as a list of places and not as a design (**Inference** from the rows):

- **Added per board:** the four composition files (`mcuboot.conf`, `mcuboot.overlay`, `app.conf`, `app.overlay`); the board devicetree with the flash node, the console and the chosen RAM; a flash configuration source; a DCD source where SDRAM exists; the board's Kconfig defaults (`DEVICE_CONFIGURATION_DATA`, `NXP_IMX_EXTERNAL_SDRAM`); and the bench values of the procedure.
- **Edited if the board differs:** the slot offsets and sizes (a devicetree overlay, as the EVKB record describes for a changed `storage` partition), the executable RAM window in `mcuboot.conf`, and the `imgtool` alignment and load address that sysbuild passes.
- **Left alone:** MCUboot's source and revision, `imgtool`, the sysbuild `SB_CONFIG_*` options, the group `crux-boot`, and the signing-key rules.
- **How to read the EVKB column:** a value from the SoC (OCRAM2, the boot header offsets for NOR) is a starting point to confirm by build. A value from the board (flash, SDRAM, pins, switches, probe) is only an example of what the product must supply.

Everything in this section is a desk result or a simulator result. The [eMMC investigation](boot-emmc-investigation.md) says it makes no eMMC support claim and adds no exit criterion to the boot or update work. The reference manual it relies on was read in a third-party-hosted copy of Rev. 3 and was not compared with the `nxp.com` document.

| Topic | What the repository's pages state | Label |
| --- | --- | --- |
| Boot partitions | The ROM reads `BOOT_PARTITION_ENABLE` (Ext_CSD[179]) and selects that boot partition, or boots from the user partition if none is named. The manual text read has no fallback between `boot0` and `boot1`; software would switch the field. | Verified by public vendor document (copy); the fallback absence is limited to the text read |
| First-stage image | The ROM copies the first 4 KB into internal RAM. The IVT, DCD and boot data must be in them. The ROM then copies the image to the destination named in the boot data (maximum 32 MB). That image is the first stage (MCUboot), not the application. It is linked for RAM, because the ROM loads it, not for XIP NOR (**Inference**). | IVT offset | `0x400` for SD and eMMC and `0x1000` for FlexSPI NOR. | SDRAM start-up | A DCD in the first 4 KB, at most 1,768 bytes, brings up SDRAM. That its writes run before the image copy is an Inference from the manual's order. **What exists.** The eMMC simulator and the power-cut replays of FatFs and Reliance Edge on `native_sim` (**Verified by command**, simulator model). The replay of MCUboot's trailer sequences on modelled cache behaviours (merged, **Verified by command**, models only): with slots on native-unit boundaries, a valid image boots and the confirmed slot stays unchanged in all 566,692 cases. A slot placed inside a native unit failed both safety properties under the torn-native model ([trailer replay](evidence/boot-emmc/trailer-replay/README.md)). A flash-API driver over the MMC disk exists only as a prototype in a Draft pull request (#435), not merged; this page does not rely on its text. `samples/boards/nxp/mimxrt1060_evk/emmc_file/boards/mimxrt1060_evk_mimxrt1062_qspi_B.overlay` swaps the EVKB's SD disk for a four-bit MMC disk to link the stack; it says the image must not be flashed to an EVKB.

**What does not exist.** An eMMC-bearing RT1060 or RT1062 target, a hardware boot result, a first-stage image for eMMC, a built eMMC header, and a decision on validation hardware (D3). The eMMC storage [physical gate](emmc-reliance-physical-gate.md) needs its own approval.

**The dependency.** An eMMC product needs the flash-API backend, which is decision D2 (adopt it, and where it lives). Until D2 is taken and a target exists, slots on eMMC cannot be built or tested end to end. eMMC adds no exit criterion to the boot or update work (plan, section 2).

## 5. The image-state contract and the recovery note on an RT1062 product

The image-state contract is adopted as Experimental for rows I1 to I7 (15 November 2026), with I8 and I9 still open ([image-state contract proposal](plans/image-state-contract-proposal.md)). Its first code is merged (#496): the public header `crux/image_state.h`, the pure functions, the portable core and a Host test double, tested on Host and in CI ([image state contract](image-state-contract.md)). No bootloader provider exists, and nothing ran on `native_sim`, in a bootloader or on a board. A design note on recovery options is a Draft pull request (#459), not merged, and this page does not cite its text. An earlier Draft prototype (#462) is still open and is not the merged code. The table uses the proposal and the investigation records.

| Question | QSPI NOR product | eMMC product |
| --- | --- | --- |
| Where the trailer lives | The last bytes of each slot in the FlexSPI window. | The last bytes of each slot, raw in the user area outside any file-system volume, written through a flash-API device that does not exist in the tree. |
| Alignment unit | Set by the flash write block. The EVKB uses `write-block-size = <1>` and `--align 1`. A part with a larger write unit changes the trailer size and the `imgtool` `--align` (the FMURT6's HyperFlash node says 16). | The driver reports it. The stack's sector is 512 B. In the replay models a layout of 4096 bytes per field (native unit) kept the safety properties; a 512 B layout let a torn write change other fields (property P7). Which unit is right depends on D8. Model result only. |
| Who writes the state | The application's request writes the trailer magic. MCUboot writes `copy_done` and erases a slot while it executes from the same NOR. That write path has the data-closure failure of issue #22, and issue #165 must be scoped before any bootloader NOR write on a board. The update agent persists the attempt record (proposal I3; where it lives is open question Q2). | The same actors, through a block device with a cache: flush after every call that touches a trailer or erases, report the erase value, and keep slots on native-unit boundaries (replay). The #22 matrix does not apply; flush and atomicity questions replace it (Inference). |
| Retained boot information | 256 B at the top of OCRAM2. Survival across the jump is Not verified (proposal Q4). | Same. |
| Recovery routes | Reprogramming through the debug probe (the EVKB flow is recorded; a product needs its own); the ROM serial downloader with a flashloader (not run, issue #309 planned); a defective but valid bootloader is not caught by the ROM fall-through. | The serial downloader, which programs SD and eMMC through a flashloader (vendor guide); the two boot partitions as two bootloader copies switched by software; power-on write protection released by a power cycle; permanent protection ends recovery of that partition (a product decision). Whether the ROM's secondary-image mechanism works with eMMC boot partitions is Not verified, and so is whether the flashloader programs an eMMC on the RT1060 (eMMC investigation, Not verified table; plan, section 7; #298 X6). |
| What is unproven | Boot, refusal of bad images, confirm, revert, update, power loss, recovery, on any board. | Those, plus everything about the ROM and an eMMC boot. |

## 6. A checklist for a new product board

Each step links the page that explains it. Steps 1 to 9 need no hardware. None of them is done for any product board.

1. Fix the scope: which variant, which flash or eMMC part, which RT1062 part and grade. Record the product values as INPUT rows of section 3 ([this page](boot-porting-rt1062.md), D8 in the [plan](plans/secure-boot-development-plan.md)).
2. Add the product board to the build: its own devicetree, with the flash node and its `jedec-id`, the chosen console and `zephyr,sram`, and an explicit board revision in the target name ([build guide](build.md)).
3. Supply the flash configuration block for the product's part and, where SDRAM exists, a DCD for its part ([Stage 3, D6 and D7](evidence/boot-update/stage3-findings.md)).
4. Create the product's four composition files in its own board folder, with the retained region and the executable window set from its memory map ([boot composition](boot-composition.md), [Stage 6, section 1.3](evidence/boot-update/stage6-layout-and-write-analysis.md)).
5. Decide the partition table and slot size from the measured signed image, with boundaries aligned to the largest erase unit ([Stage 6](evidence/boot-update/stage6-layout-and-write-analysis.md)).
6. Build, sign with a test key and check the result with a script for the product board ([check script](../scripts/test-boot-composition.sh), section 2 of this page). Record what was built, not that it boots.
7. Choose the key plan and keep every key outside the repository ([review, section 3](secure-boot-and-update-review.md)).
8. eMMC only: take the D8 inputs, decide D2 and D3, and design the first-stage header and provisioning ([eMMC investigation](boot-emmc-investigation.md), [trailer replay](evidence/boot-emmc/trailer-replay/README.md)).
9. Rewrite the bench values for the product: probe, flash algorithm, backup and no-touch ranges, boot-mode access, power-cut fixture ([board test procedure](secure-boot-board-test-procedure.md), [image profiles](board-image-profiles.md)).
10. Settle the recovery level for the product and prove a non-destructive recovery path before any boot experiment ([updating or recovering a bootloader](boot-bootloader-update-investigation.md)).
11. Obtain the task-specific hardware approval and the decision on issue #165, then run the cases of the procedure and record each result separately from the build ([board test procedure](secure-boot-board-test-procedure.md)).
12. Declare the trust level reached and what was not shown ([plan, section 3](plans/secure-boot-development-plan.md)).

## 7. Not verified

- That the boot ROM accepts any header of this repository on any board, and that it runs a DCD before the jump.
- A build of any product board, a product FCB or DCD, and an eMMC first-stage image or header.
- The offset of the IVT inside an eMMC boot partition, and the card and uSDHC state at hand-over.
- The erase unit the update path can rely on, the erase time of a whole slot, and the effect of the missing watchdog.
- That retained boot information survives the jump to an SDRAM image.
- Whether the reference manual copy equals the `nxp.com` document, and the JEDEC eMMC standard (not read).
- Any behaviour on a board: boot, refusal, confirm, revert, update, power loss and recovery.
