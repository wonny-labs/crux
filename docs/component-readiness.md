# Component readiness

One table: what exists for each component, in which environments, with which evidence, and what is missing. It is a reading aid over the sources it cites. It adds no decision, no approval and no claim beyond those sources. A cell says `unknown` where the sources do not settle it. The code, the tests and CI at your revision are authoritative; where a cell and the code differ, the code wins.

For the contracts and a prose inventory, see the [capability inventory](architecture.md#current-capability-integration). It is not a qualification matrix, and neither is this table.

## How to read this

**Evidence levels.** A cell names the highest level that the repository records for the component's current code, then the other levels that exist. A higher level is closer to a board. It does not include the lower ones: none implies another, as [Getting started](getting-started.md#8-supported-environments) and [AGENTS.md](../AGENTS.md#validation-and-evidence) state.

- **E1 Host test.** CTest, GoogleTest or Python tests on Linux Host, with fakes or a Host provider. It does not prove Zephyr behaviour, timing or any board.
- **E2 `native_sim`.** Ztest, Twister or an image on Zephyr `native_sim`, with the host TCP stack and test entropy. It does not prove target peripherals, timing or persistence.
- **E3 EVKB build.** The selection compiles and links for `mimxrt1060_evk@B//qspi` and nothing runs. It does not prove boot, peripheral behaviour or resource use.
- **E4 physical board.** A recorded run of identified firmware on an identified board, limited to its documented scenario. It does not prove other boards, cards, wiring or endurance, nor the current code if the run was of earlier code.

The validation limits are in [Getting started](getting-started.md#8-supported-environments) (Host tests, `native_sim` runs and target cross-builds do not prove physical operation) and in [Engineering and validation boundaries](architecture.md#engineering-and-validation-boundaries). A board run that was inconclusive, or that ran code since replaced by a redesign, is named in the cell and is not counted as E4. A completed run of earlier code counts only as its narrow slice. Where a result is a narrow slice, the cell says which slice ([status of a hypothesis or exit criterion](architecture.md#status-of-a-hypothesis-or-exit-criterion)) and links the record that holds the run.

**Zephyr composition** means what the repository builds, not what a product could build:

- `module` means the selection is in `zephyr/CMakeLists.txt` and `zephyr/Kconfig`, with the port under `components/<name>/ports/zephyr`.
- `tests/ only` means every composition that selects it sits under `tests/`.
- `samples/` or `templates/` is named where a composition outside `tests/` exists.
- `none` means no Zephyr selection or port exists for it.
- Compositions in other repositories are not counted.

**Provisional tier.** The tier is [ADR-0001 Decision 4](decisions/0001-application-boundary-and-api-stability.md#decision-4-api-stability-and-change-policy) applied to what this table records. Nothing is Stable, because nothing is Stable before `v1.0`. Each row shows one of these outcomes:

- **Experimental** where the public header carries a `Status: Experimental` line, or where the rule forces it: no Zephyr composition outside `tests/` in this repository.
- **Unstable** where the Zephyr composition outside `tests/` and the rest of the ADR's description ("an adopted contract with a consumer and tests") are all shown by the sources cited in the row.
- **Unassigned** or **Internal** otherwise, as stated in the cell.

ADR-0001 is Accepted. A tier has not yet been assigned to each interface, and only some public headers carry a `Status:` line, so every tier here stays provisional.

## Readiness table

**Frozen for new product code.** `thread`, `sync` and `serial` are frozen for new product code (see [Choosing an API](choosing-an-api.md); `queue` was frozen too and is now removed, see its row): no new features and no real-time extension, existing users keep working, and no deprecation has been decided. Use Zephyr threads, locks, message queues and UART drivers instead. `gpio`, `i2c` and `spi` are frozen as Experimental by [ADR-0001](decisions/0001-application-boundary-and-api-stability.md), with deprecation planned at the first tag and removal in the next tagged release; neither step is done, and new product code uses Zephyr's GPIO, I2C and SPI APIs. The freeze is not a tier. These rows keep their provisional tier and evidence.

## Notes

- **Board results are narrow slices of earlier code.** `file` on the microSD has one board and one card, on the source revisions named in its records, and is not a result for the current code. Netif and Sockets have one narrow, non-qualifying E4 run. The Time and controller-sample runs are of code since replaced by a redesign and are not counted. The GPIO physical check is a plan with no result.
- **Management components.** Nothing ran on a board ([guide](management-in-a-product.md)). Every one is at most E3.
- **E3 is a build.** The Mbed image and the bench image compile and link; the bench image also refuses to start. Neither shows that a handshake, a login, entropy or timing work on the board.
- **Out-of-tree consumers.** Compositions in other repositories are not counted above. If one exists for a component marked Experimental, the label needs that record before it changes.
- **Where the cells come from.** Each cell is read from `components/<name>/CMakeLists.txt`, the files under `ports/`, `zephyr/Kconfig`, `zephyr/CMakeLists.txt`, [tests/README.md](../tests/README.md), the cited contract or validation document and, for E4, the evidence directory itself. Where the sources conflict, the cell names the one that holds.
